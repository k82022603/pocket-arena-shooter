## 1. 개요

### 1.1 컨셉 한 줄 요약
> **"앱 설치 없이, 옆 사람과 QR 한 번 찍고 바로 붙는 파티마 탑다운 2인 슈팅"** — 『파이브 스타 스토리』의 파티마를 조종해 근거리 2인 대전/협동을 즐기는 모바일 브라우저 트윈스틱 슈터 (팬 게임).

### 1.2 핵심 특징
| # | 특징 | 설명 |
|---|------|------|
| 1 | **제로 인스톨** | URL 접속만으로 실행. 앱스토어/설치 불필요. PWA로 홈 화면 추가 가능 |
| 2 | **근거리 즉시 페어링** | QR코드 또는 6자리 코드로 5초 내 연결. Android Chrome에서는 NFC 탭/Bluetooth 보조 발견 지원(선택) |
| 3 | **저지연 P2P 동기화** | WebRTC DataChannel 기반 P2P. 같은 Wi‑Fi/핫스팟이면 10~30ms 수준 |
| 4 | **짧고 강한 세션** | 1판 60~90초. 대기 시간 최소화, 재대결 원터치 |

### 1.3 장르 / 시점 / 플랫폼
- 장르: 탑다운 아레나 슈터(트윈스틱)
- 시점: 2D 탑다운, 가로(landscape) 고정
- 플랫폼: 모바일 웹 브라우저 (1순위 Android Chrome, 2순위 iOS Safari)

## 3. 게임 디자인

### 3.1 게임 모드
| 모드 | 인원 | 시간 | 설명 | 승패 조건 |
|------|------|------|------|-----------|
| **듀얼 (1:1 대전)** | 2 | 90초 | 원형/사각 아레나에서 서로 사격. 장애물 뒤 엄폐 가능 | 3라운드 중 2선승. 라운드: 상대 HP 0 또는 시간 종료 시 HP 높은 쪽 승 |
| **웨이브 디펜스 (협동)** | 2 | 3~5분 | 중앙 코어를 지키며 몰려오는 적 웨이브 처치 | 10웨이브 클리어 시 승리. 코어 HP 0 또는 두 명 모두 다운 시 패배 |
| **솔로 서바이벌** | 1 | 무제한 | 연결 없이 혼자 점수 경쟁(연습/대기용) | 사망 시 종료, 최고 점수 기록 |

- 솔로 모드는 페어링 대기 중에도 플레이 가능하도록 하여 "대기 시간 = 0"을 노림.
- 협동 모드는 대전 모드 이후(M4)에 추가. 코어 로직(적 AI, 스폰)은 호스트가 전담.

### 3.2 조작 방식 (모바일 터치)
**기본: 트윈스틱 + 보조 버튼, 가로 화면 고정**

| 입력 | 위치 | 동작 | 상세 |
|------|------|------|------|
| 좌측 가상 조이스틱 | 화면 좌하단 (터치 시작점에 생성되는 플로팅 방식) | 이동 | 데드존 15%, 최대 반경 60px, 8방향이 아닌 아날로그 |
| 우측 가상 조이스틱 | 화면 우하단 (플로팅) | 조준 + 자동 발사 | 기울인 방향으로 조준, 반경 30% 이상 밀면 자동 연사 |
| 대시 버튼 | 우측 조이스틱 위쪽 | 짧은 회피 | 쿨다운 2초, 대시 중 0.2초 무적 |
| 스킬 버튼 (선택) | 좌측 조이스틱 위쪽 | 캐릭터 고유 스킬 | 예: 방어막, 산탄 |
| 일시정지 | 좌상단 | 메뉴 | 멀티 모드에선 "나가기 확인"만 |

- **한 손 모드 대안**: 우측 스틱 대신 "가장 가까운 적 자동 조준 + 발사 버튼" 옵션 제공 (접근성).
- 멀티터치 필수: `touchstart/touchmove/touchend` 를 pointerId 단위로 추적. `touch-action: none`, 브라우저 제스처(뒤로가기 스와이프, 당겨서 새로고침) 차단.
- 햅틱: `navigator.vibrate` (Android만 동작, iOS 무시).

### 3.3 캐릭터 / 무기 (MVP 범위)
플레이어는 FSS의 **파티마** 중 하나를 골라 조종한다. 원작의 파워게이지를 게임 능력치(이동속도·HP·화력·대시)로 추상화하며, 상세는 [캐릭터_설정.md](캐릭터_설정.md).

| 파티마 | 역할 | 특징 |
|--------|------|------|
| 라키시스 | 올라운더 | 전 능력 평균 이상, 대시 쿨다운 짧음 |
| 클로소 | 스피드형 | 최고 이동속도·대시, HP 낮음 |
| 아트로포스 | 화력형 | 데미지·연사 우위, 속도 보통 |
| 에스트 | 방어형 | HP 최고, 느림, 대시 무적 시간 김 (밧슈 탑승 보정 컨셉) |

| 항목 | MVP | 비고 |
|------|-----|------|
| 캐릭터 | 파티마 4종 (위 표), 아트는 임시 실루엣 | 스프라이트는 이후 교체 |
| 기본 무기 | 연사 라이플 (기준 탄속 900px/s, 6발/초, 데미지 10) | 기준 HP 100, 캐릭터별 보정 |
| 아레나 픽업 | 산탄총(10초), 힐팩(+30), 속도 부스트(5초) | 15초 간격 랜덤 스폰, 호스트가 결정 |
| 장애물 | 아레나당 4~6개 고정 박스 | 탄환 차단, 이동 차단 |

### 3.4 규칙 세부
- **라운드 시작**: 3초 카운트다운 동안 이동 불가.
- **스폰**: 아레나 양 끝 고정 위치, 라운드마다 좌우 교대.
- **동점 처리**: 시간 종료 시 HP 동일 → 서든데스 15초(HP 1로 고정, 첫 피격 패배).
- **연결 끊김**: 5초 내 재연결 시 라운드 재개(상태 스냅샷 재전송), 실패 시 남은 쪽 승리 처리.
- **웨이브 디펜스 부활**: 다운된 아군 근처에서 2초 유지 시 부활(HP 50%).

## 4. 기술 아키텍처

### 4.1 프론트엔드 스택 추천
| 후보 | 장점 | 단점 | 판정 |
|------|------|------|------|
| **Phaser 3** | 씬/입력/Arcade 물리/스프라이트 애니/타일맵/오디오 내장. 모바일 터치 처리 성숙. 2D 슈터 레퍼런스 풍부 | 번들 1MB+ (트리쉐이킹 제한적). 렌더 커스터마이징은 PixiJS보다 제약 | **채택** |
| PixiJS | 가장 가벼운 고성능 2D 렌더러. 세밀한 제어 | 게임 루프/물리/입력/씬 관리 전부 직접 구현 → 일정 부담 | 보류 (Phaser가 무거워지면 전환) |
| Three.js | 3D 연출 가능 | 이 게임은 2D 탑다운, 3D 불필요. 저사양 모바일 발열/배터리 부담 | 제외 |

**최종 스택**
- 언어/빌드: TypeScript + Vite (PWA 플러그인 포함)
- 렌더/게임: Phaser 3 (WebGL, Canvas 폴백)
- 네트워크: 브라우저 표준 `RTCPeerConnection` 직접 사용 (래퍼 없이 얇게), 폴백 WebSocket
- 시그널링 서버: Node.js + `ws` (또는 Cloudflare Workers + Durable Objects: 상시 서버 없이 방 단위 상태 유지)
- STUN/TURN: 공개 STUN + 자체 coturn 1대 (셀룰러 간 연결 폴백)
- 상태 저장(선택): 랭킹용 경량 DB (SQLite/PlanetScale 등), MVP는 없음

### 4.2 전체 시스템 구조 (텍스트 다이어그램)
```
[Phone A: 브라우저]                          [Phone B: 브라우저]
 ┌───────────────────────┐                   ┌───────────────────────┐
 │ UI Layer (HTML/CSS)   │                   │ UI Layer               │
 │  타이틀/로비/QR/결과   │                   │                        │
 ├───────────────────────┤                   ├───────────────────────┤
 │ Game Layer (Phaser 3) │                   │ Game Layer (Phaser 3) │
 │  Scene: Boot/Title/   │                   │                        │
 │   Lobby/Arena/Result  │                   │                        │
 ├───────────────────────┤                   ├───────────────────────┤
 │ Sim Core (순수 TS)     │ ◄── 동일 코드 ──► │ Sim Core               │
 │  틱 60Hz, 결정적 로직   │                   │  (클라이언트: 예측+보간) │
 │  HOST 권위 실행         │                   │                        │
 ├───────────────────────┤                   ├───────────────────────┤
 │ Net Layer             │                   │ Net Layer             │
 │  Transport 인터페이스   │                   │                        │
 │   ├ WebRTC DataChannel│◄═══ P2P (LAN/STUN) ═══►│ WebRTC DataChannel │
 │   ├ WebSocket Relay   │──┐               ┌──│ WebSocket Relay      │
 │   └ (opt) BLE Bridge  │  │               │  │                        │
 └───────────┬───────────┘  │               │  └───────────┬───────────┘
             │ 시그널링(방 생성/참가, SDP/ICE) │               │
             ▼              ▼               ▼              ▼
        ┌────────────────────────────────────────────────┐
        │  Signaling / Relay Server (Node ws or CF DO)    │
        │   - 방 코드(6자리) ↔ 소켓 매핑                    │
        │   - SDP/ICE 중계, P2P 실패 시 게임 패킷 릴레이     │
        └────────────────────────────────────────────────┘
                     │
        ┌────────────┴───────────┐
        │  STUN (공개) / TURN(coturn) │  ← 셀룰러↔셀룰러 폴백
        └────────────────────────┘
```

**레이어 규칙**
- `Sim Core`는 Phaser/DOM/네트워크에 의존하지 않는 순수 TS 모듈 → 단위 테스트 및 로컬 2인 시뮬레이션(M2) 가능.
- `Net Layer`는 `Transport` 인터페이스(`send(bytes)`, `onMessage`, `rtt`)로 추상화 → WebRTC/WebSocket/BLE 브리지를 교체 가능.

### 4.3 상태 동기화 전략
| 항목 | 결정 | 이유 |
|------|------|------|
| 권위 모델 | **호스트 권위(Host-authoritative)**. 방을 만든 쪽이 호스트, 서버 없음 | 2인 게임에서 가장 단순. 적 AI/픽업/판정을 한 곳에서 결정 → 불일치 없음 |
| 시뮬레이션 틱 | 60Hz 고정 스텝 (`accumulator` 방식), 렌더는 rAF | 기기별 프레임 차이와 무관하게 결정적 결과 |
| 입력 전송 빈도 | **30Hz** (2틱마다 1패킷), 패킷에 최근 3틱 입력을 중복 포함(redundancy) | 패킷 손실 시 재전송 없이 복구, 대역폭 ~3KB/s |
| 스냅샷 전송 | 호스트 → 게스트 **20Hz**, 델타 압축 없이 전체 상태(2인+탄환 ≤ 40개 → 약 300~500B) | 단순함 우선. 대역폭 10KB/s 이내 |
| 게스트 자기 캐릭터 | **클라이언트 측 예측** + 호스트 스냅샷으로 재조정(reconciliation) | 조작감 즉답성 확보 |
| 상대/적/탄환 | **스냅샷 보간(interpolation)**, 100ms 버퍼(2스냅샷) | 끊김 없는 움직임 |
| 피격 판정 | 호스트가 판정. 게스트 사격은 "발사 의도"만 전송, 탄 생성은 호스트 | 지연 보상: 호스트가 게스트 RTT/2만큼 되감기(rewind)해서 판정 (최대 150ms) |
| 시간 동기 | 연결 직후 5회 핑으로 오프셋/RTT 측정, 이후 매 2초 갱신 | 보간 버퍼 및 되감기 계산 기준 |
| 채널 | DataChannel 2개: `input`(unordered, maxRetransmits:0) / `event`(ordered, reliable: 라운드 시작·종료·픽업·재접속 스냅샷) | 지연 민감 데이터와 신뢰 필요 데이터 분리 |
| 직렬화 | `ArrayBuffer` + `DataView` 수동 바이너리 (JSON 금지) | 패킷 크기 1/5 이하, BLE MTU 대응 시 재사용 |
| 랜덤 | 시드 기반 PRNG(xorshift), 시드는 호스트가 라운드 시작 시 배포 | 픽업/적 스폰 재현 |

**입력 패킷 포맷(안, 12바이트)**
```
[0]   uint8   packetType (0x01=INPUT)
[1-2] uint16  tick (호스트 기준 틱 번호, wrap)
[3]   int8    moveX  (-127~127)
[4]   int8    moveY
[5]   int8    aimX
[6]   int8    aimY
[7]   uint8   buttons (bit0 fire, bit1 dash, bit2 skill)
[8-11]        직전 2틱 입력 요약(중복, 각 2바이트)
```

## 5. 블루투스 근거리 멀티플레이어 설계

### 5.1 핵심 사실 정리 (반드시 인지)
| 사실 | 영향 |
|------|------|
| **Web Bluetooth API는 iOS의 모든 브라우저에서 미지원** (Safari, iOS Chrome/Edge/Firefox 모두 WebKit 강제 → 동일하게 불가) | 한국 스마트폰 시장 iPhone 점유율(약 25~30%)이 통째로 제외됨. **프로젝트 최대 리스크** |
| 지원 브라우저: Android Chrome, Samsung Internet, Edge/Opera(Android), 데스크톱 Chrome/Edge. Firefox 미지원 | "Android Chromium 계열 한정" |
| 브라우저는 **Central(클라이언트) 역할만 가능**. Peripheral(광고/GATT 서버) 역할 API 없음 | **폰 브라우저 ↔ 폰 브라우저 직접 연결은 원천적으로 불가능.** 양쪽 모두 "찾는 쪽"이라 서로 발견조차 못 함 |
| 기기 선택은 반드시 사용자 제스처 + 브라우저 네이티브 기기 선택 팝업(`requestDevice`) 경유 | 자동 매칭 UX 불가, 매번 팝업 |
| HTTPS 필수, 백그라운드 전환 시 연결 유지 불안정 | 홈 버튼/알림 확인 시 끊김 잦음 |
| ATT 기본 MTU 23바이트(유효 페이로드 20B). Android는 OS가 자동 협상(최대 517)하지만 **Web Bluetooth에서 MTU 조회/협상 API 없음** | 패킷을 20바이트 이하로 설계해야 안전 |
| 특성값 최대 512바이트, `writeValueWithoutResponse` 처리량 실측 수 KB/s 수준, 연결 간격 7.5~50ms | 20Hz 스냅샷 전송에는 부족, 입력 전송(12B×30Hz)은 가능 |
| PWA(홈 화면 추가)로 설치해도 **브라우저 엔진의 API 제약은 동일** — iOS PWA에서도 Web Bluetooth 불가, 백그라운드 실행 불가, 푸시는 iOS 16.4+ 제한적 | PWA는 "설치 경험 개선"일 뿐 기술 제약 해결책이 아님 |

> 결론: **"블루투스로 폰끼리 연결"은 모바일 웹에서 그대로는 구현이 불가능**하다. "블루투스"라는 요구는 실제로는 **"옆 사람과 서버 없이/간편하게 붙고 싶다"는 사용자 가치**로 재해석해야 하며, 이를 만족하는 대체 기술을 선택해야 한다.

### 5.2 Web Bluetooth GATT 연결 흐름 (참고: BLE 브리지 방식 채택 시)
브라우저가 Central이므로, 반드시 **외부 Peripheral 장치**(예: ESP32 보드, 라즈베리파이 등 BLE 서버 프로그램)가 있어야 한다. 아래는 "BLE 브리지 장치"가 두 폰의 패킷을 중계하는 흐름이다.

| 단계 | 호출 / 동작 | 비고 |
|------|-------------|------|
| 1 | 사용자가 "블루투스로 연결" 버튼 탭 (사용자 제스처) | 제스처 없으면 SecurityError |
| 2 | `navigator.bluetooth.requestDevice({ filters:[{ services:[GAME_SERVICE_UUID] }] })` | 브라우저 기기 선택 팝업 표시, 사용자가 브리지 선택 |
| 3 | `device.gatt.connect()` | 연결 간격은 OS가 결정. 타임아웃 10초 처리 |
| 4 | `server.getPrimaryService(GAME_SERVICE_UUID)` | 커스텀 128bit UUID |
| 5 | `service.getCharacteristic(INPUT_TX_UUID)` (Write Without Response) | 폰 → 브리지 입력 전송용 |
| 6 | `service.getCharacteristic(STATE_RX_UUID)` → `startNotifications()` + `characteristicvaluechanged` 리스너 | 브리지 → 폰 상태 수신용 |
| 7 | 슬롯 배정: 브리지가 `SLOT_UUID` Read로 P1/P2 반환 | 먼저 연결한 쪽 = 호스트(P1) |
| 8 | 게임 루프: 30Hz로 `writeValueWithoutResponse(12바이트 입력)` | 20바이트 이하 유지 |
| 9 | 브리지는 P1 입력을 P2에, P2 입력을 P1에 notify로 그대로 중계 (또는 호스트 스냅샷 중계) | 브리지 자체는 로직 없음 |
| 10 | `gattserverdisconnected` 이벤트 → 3회 재연결 시도 후 실패 시 게임 종료 | 백그라운드 전환 대응 |

**BLE 브리지 방식에서의 데이터 설계**
- 입력 12B 패킷 → 그대로 사용(20B 제한 내).
- 스냅샷은 20B 초과 → **입력 교환 기반 결정적 락스텝(deterministic lockstep)** 으로 전환해야 함(양쪽이 서로의 입력만 받아 동일 시뮬레이션 실행). 즉 BLE 경로에서는 동기화 모델 자체가 달라짐 → 코드 복잡도 증가.
- 실측 목표: 편도 지연 30~60ms, 손실률 1% 미만. 이보다 나쁘면 입력 지연 2~3틱 추가.

### 5.4 최종 추천 아키텍처
**추천: C (QR/6자리 코드 + WebRTC DataChannel)를 주 경로, D (WebSocket 릴레이)를 자동 폴백, E (Web NFC)를 Android 보조 페어링으로 채택. Web Bluetooth는 "옵션 실험 기능(A')"으로 격리.**

| 결정 | 근거 |
|------|------|
| 주 전송을 WebRTC로 | iOS 포함 전 플랫폼 지원, 근거리(같은 공유기/핫스팟)일 때 mDNS/host 후보로 사실상 LAN 직결이라 "블루투스급" 지연 확보 |
| 페어링을 QR + 6자리 코드 이중화 | QR은 카메라 권한/조명 문제 발생 시 6자리 코드로 즉시 대체. 코드는 시그널링 서버 방 ID |
| 릴레이 자동 폴백 | 사내 Wi‑Fi(클라이언트 격리), 이동통신사 대칭 NAT 환경에서 P2P 실패 시 5초 내 자동 릴레이 전환. 사용자에겐 "연결됨"만 보임 |
| Bluetooth는 "요구사항 재정의"로 대응 | 요구의 본질(근거리, 간편, 설치 없음)은 C+E로 충족. 진짜 BLE 전송이 필요한 경우(오프라인 부스)만 A' 브리지를 별도 트랙으로 검토 |
| Transport 추상화 유지 | 향후 Local P2P API 정식화 또는 BLE 브리지 추가 시 게임 로직 변경 없이 교체 |

**연결 시퀀스 (C 경로)**
```
호스트 폰                         시그널링 서버                    게스트 폰
  │ 1. "방 만들기"                     │                               │
  │──── create_room ─────────────────►│                               │
  │◄─── room_code(6자리) + QR ────────│                               │
  │ (QR 화면 표시)                     │      2. QR 스캔/코드 입력       │
  │                                   │◄──── join_room(code) ─────────│
  │◄─── peer_joined ──────────────────│                               │
  │ 3. createOffer → setLocal         │                               │
  │──── offer(SDP) ──────────────────►│──── offer ───────────────────►│
  │                                   │◄─── answer(SDP) ──────────────│
  │◄─── answer ───────────────────────│                               │
  │◄═══════ ICE 후보 교환(양방향, trickle) ══════════════════════════►│
  │ 4. DataChannel open (input/event) │                               │
  │◄═══════════════ P2P 직결 (LAN 우선, STUN, 최후 TURN) ═════════════►│
  │ 5. 5초 내 open 실패 → 양쪽 relay 모드 전환 (같은 서버 WS 사용)     │
  │ 6. 시간 동기 핑 5회 → 라운드 시작 이벤트(reliable) → 게임          │
```

**Web Bluetooth를 넣는 경우의 최소 조건(체크리스트)**
- [ ] Android Chrome 전용 실험 메뉴로 격리, iOS에서는 버튼 자체를 노출하지 않음 (`'bluetooth' in navigator` 체크)
- [ ] 외부 브리지 장치 펌웨어(ESP32, NimBLE) 및 UUID 스펙 별도 문서화
- [ ] 락스텝 동기화 모드가 Sim Core에서 옵션으로 지원됨
- [ ] 브리지 없이 실패 시 즉시 C 경로로 안내

| 로비 | P1/P2 아바타·연결 상태(P2P/릴레이 아이콘, RTT ms), 모드 선택 카드 2개(호스트만 변경), "준비" 토글 |
| 아레나(HUD) | 좌상 P1 HP바, 우상 P2 HP바, 중앙상단 타이머·라운드 스코어, 좌하/우하 플로팅 스틱 영역(반투명 가이드 원), 우측 스틱 위 대시 버튼. 좌상단 작은 일시정지 |
| 결과 | 승패 텍스트, 라운드별 스코어, 명중률·처치 수, 하단 "재대결" 대형 버튼(상대도 누르면 즉시 시작) |

### 6.3 모바일 UX 세부 규칙
- `viewport-fit=cover` + `env(safe-area-inset-*)` 로 노치/홈 인디케이터 회피.
- 화면 잠금 방지: `navigator.wakeLock.request('screen')` (iOS 16.4+, Android 지원).
- iOS Safari 전체화면 불가 → 주소창 최소화를 위해 세로 스크롤 방지 + 100dvh 사용. PWA 설치 시 `display: standalone` 으로 해결.
- 첫 터치 시 오디오 컨텍스트 unlock (iOS 자동재생 정책).
- 진동/사운드 토글을 HUD 밖 설정에 배치.
- 저사양 판정(디바이스 메모리·첫 3초 fps) 시 파티클/그림자 자동 축소.

## 7. 개발 마일스톤 및 일정

| 단계 | 기간 | 산출물 | 완료 기준 |
|------|------|--------|-----------|
| **M0. 기술 검증 (PoC)** | 1주 | (a) Android Chrome Web Bluetooth ↔ ESP32 브리지 20B 왕복 지연 측정 (b) iOS Safari ↔ Android Chrome WebRTC DataChannel LAN/셀룰러 연결 성공률·RTT 측정 (c) Phaser 3 빈 씬 60fps 확인 | PoC 보고서, **주 경로 최종 확정(C 예상)**, BLE 트랙 지속 여부 결정 |
| **M1. 싱글 프로토타입** | 2주 | 아레나 1개, 이동/조준/발사/피격/HP, 플로팅 트윈스틱, 솔로 서바이벌 | 실기기 3종(중급 Android, iPhone, 저사양 Android)에서 55fps 이상 |
| **M2. 로컬 2인 임시 동기화** | 1.5주 | Sim Core 분리, 같은 브라우저 안에서 호스트/게스트 두 인스턴스를 `MessageChannel`로 연결한 **가짜 네트워크(지연·손실 주입)**, 예측/보간/되감기 구현 | 200ms/5% 손실 주입에서도 게임 플레이 가능. 결정성 테스트 통과 |
| **M3. 실제 연결 (WebRTC + 릴레이)** | 2.5주 | 시그널링 서버, QR/코드 페어링, DataChannel 2채널, 릴레이 자동 폴백, 재접속, 1:1 대전 룰(3라운드) | 서로 다른 OS 두 기기 대전 성공률 95%(LAN), 85%(셀룰러) |
| **M4. 협동 웨이브 디펜스** | 2주 | 적 AI 3종, 스폰 스케줄, 코어, 부활, 픽업 | 10웨이브 플레이 가능, 호스트 CPU 프레임 예산 내 |
| **M5. 폴리싱·PWA·테스트** | 2주 | 아트/사운드 정리, 결과 화면, PWA 매니페스트/서비스워커, 저사양 대응, 유저 테스트 20명 | KPI(2.3) 측정, 크래시/끊김 이슈 정리 |
| **(선택) M6. BLE 브리지 트랙** | 2주 | ESP32 펌웨어, 락스텝 모드, Android 전용 실험 메뉴 | 오프라인 환경 대전 성공 |

- 총 **약 11~12주** (M6 제외). 1~2인 개발 기준.
- M0 결과에 따라 M3 범위가 바뀌므로, M0 종료 시 본 문서 5장 갱신 필수.
