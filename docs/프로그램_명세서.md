## 1. 개요

### 1.1 목적
같은 Wi‑Fi에 있는 두 사람이 설치 없이 브라우저만으로 1:1 대전 또는 협동 방어전을 하는 모바일 웹 탑다운 슈팅 게임이다. 혼자 하기(봇 대전·1인 방어)도 지원한다.

### 1.2 범위

| 포함 | 제외 |
|------|------|
| 웹 클라이언트(게임), 시그널링·릴레이 서버, 공용 프로토콜 타입, 개발·검사 스크립트 | 계정·로그인, 서버 저장 전적, 공개 랭킹, 결제, 3인 이상 |

### 1.3 실행 환경

| 구분 | 요구 사항 |
|------|-----------|
| 클라이언트 | 최신 Chrome·Safari·Edge (WebGL 또는 Canvas, WebRTC DataChannel, Web Audio). 가로 화면 |
| 시그널링 서버 | Node.js 22 이상 |
| 개발 PC | Node.js 22 이상, npm 10 이상. Windows·macOS·Linux |
| 네트워크 | 두 기기가 같은 LAN(권장). P2P가 안 되면 시그널링 서버 경유 릴레이 |

### 1.4 기술 스택

| 영역 | 사용 |
|------|------|
| 언어 | TypeScript 5 (ES2022) |
| 게임 엔진 | Phaser 3 |
| 빌드 | Vite 6, vite-plugin-pwa |
| 네트워크 | 브라우저 표준 RTCPeerConnection·WebSocket, 서버는 `ws` |
| QR | `qrcode`(생성), BarcodeDetector 또는 `jsqr`(인식) |
| 실행기 | `tsx` (TypeScript 스크립트·서버 실행) |

## 2. 시스템 구성

### 2.1 프로세스 구성

```
[기기 A 브라우저]  ── WebRTC DataChannel (P2P, 게임 데이터) ──  [기기 B 브라우저]
      │                                                            │
      └──── WebSocket (방 코드·협상·릴레이) ──── [시그널링 서버] ──┘
                                                 Node, 포트 8787
```

개발 중에는 PC 한 대가 웹 서버(Vite, 5173)와 시그널링 서버(8787)를 함께 띄운다. 웹 서버가 `/ws` 경로를 시그널링 서버로 넘기므로 기기는 5173 하나만 알면 된다.

### 2.2 모듈 계층

```
apps/web/src
  sim/   게임 규칙 (Phaser·DOM·네트워크를 모른다. Node에서도 돈다)
   ↑
  net/   전송 계층 (WebRTC·릴레이·시그널링·재접속)
   ↑
  game/  화면·입력·연출·동기화 (Phaser)
  ui/    DOM 오버레이 (코드 입력·QR 스캐너·토스트)
```

**의존 규칙**: 화살표 방향으로만 가져다 쓴다. `sim/`은 아무것도 가져오지 않는다. 이 규칙 덕분에 같은 규칙 코드가 호스트·참가자 예측·헤드리스 검사에서 그대로 돈다.

### 2.3 게임 방식별 역할

| 방식 | 동기화 구현 | 권위 | 네트워크 |
|------|------------|------|---------|
| 혼자 하기 | `SoloSync` | 이 기기 | 없음 |
| 방을 만든 쪽 | `HostSync` | 이 기기 (시뮬레이션을 돌린다) | 참가자 입력 수신, 스냅샷 20Hz 송신 |
| 참가한 쪽 | `GuestSync` | 방을 만든 쪽 | 입력 60Hz 송신, 스냅샷 수신 (예측·보간) |

## 4. 프로그램 상세 명세

각 항목은 **기능 / 입력 / 처리 / 출력 / 주요 함수**로 적는다.

### SIM-01 시뮬레이션 코어 (`sim/core.ts`)

**기능**: 게임 규칙의 중심. 같은 상태와 같은 입력이면 항상 같은 결과를 낸다(결정적).

| 함수 | 입력 | 출력 | 설명 |
|------|------|------|------|
| `createInitialState(characters, opts)` | 파티마 2명, `{mode, playerCount, seed, difficulty?}` | `SimState` | 새 경기. 대전은 양 끝, 협동은 코어 양옆에서 시작 |
| `step(state, inputs, opts?)` | 상태, 두 플레이어 입력, `{inputTicks, bulletLag, history, onEvent}` | 없음 (상태 변경) | 한 틱 진행 |
| `applyPlayerInput(p, input)` | 플레이어, 입력 | 없음 | 타이머 감소·대시·무기 교체·이동·넉백 감쇠·조준. 참가자 예측도 이것을 쓴다 |
| `consumeFire(p, input)` | 플레이어, 입력 | 발사 여부 | 쿨다운이 끝났고 방아쇠를 당겼으면 true, 쿨다운 설정 |
| `makeBullets(p, firstId, spawnTick, lagTicks)` | | `BulletState[]` | 산탄 펼침, 결정적 흔들림 |
| `damagePlayer(state, target, amount, by, onEvent?)` | | 실제 피해량 | 체력·통계·사건 |
| `knockPlayer(p, nx, ny, speed)` | | 없음 | 넉백 속도 부여 (더 센 쪽 유지) |
| `outcomeOf(state)` | | `Outcome` 또는 null | 승패 판정 |
| `summarize(state)` | | `MatchSummary` | 결과 화면용 복사본 |
| `setPlayerCharacter`, `setPlayerLoadout` | | 없음 | 상대 선택 반영, 기본 무기 설정 |

**`step` 처리 순서**
1. `tick`, `elapsed` 증가
2. 살아 있는 플레이어마다 `applyPlayerInput` → 대시 시작이면 대시 수 증가 → `consumeFire`면 탄 생성, 발사 수(탄알 단위) 증가
3. 위치 기록(`history.record`, 협동이면 적 위치도)
4. 탄환 이동·판정(`stepBullets`): 적 탄은 플레이어 → 코어 순, 협동의 플레이어 탄은 적만(되감기 적용), 대전 탄은 상대만(되감기·대시 무적 적용). 관통탄은 맞힌 대상을 기억하고 계속 난다
5. 픽업 스폰·획득(`stepPickups`)
6. 협동이면 `stepCoop`

**승패**: 대전은 한쪽 체력 0. 협동 패배는 코어 0 또는 뛰는 사람 전원 다운, 승리는 10웨이브 스폰 종료 후 적 0.

### SIM-02 협동 규칙 (`sim/coop.ts`)

| 함수 | 설명 |
|------|------|
| `waveComposition(wave, playerCount, difficulty)` | 척후병 `2+2w`(최소 1), 포수 `⌊w/2⌋`, 강습병 `⌊(w-1)/2⌋`(3웨이브부터). 1인이면 난이도 배율을 곱해 반올림. 척후병 2 → 포수 1 → 강습병 1 순으로 섞는다 |
| `stepCoop(state, onEvent)` | 웨이브 → 적 → 죽은 적 제거 → 부활 |
| `activePlayers(state)` | 이번 경기에서 뛰는 플레이어 (1인이면 앞 한 명) |

**웨이브 상태 기계**

| 단계 | 이름 | 처리 | 전이 |
|------|------|------|------|
| 0 | 대기 | 타이머 감소 | 0이 되면 웨이브 +1, 편성 생성 → 1 |
| 1 | 스폰 | 40틱마다 한 기, 네 변 중 무작위 위치 | 큐가 비면 → 2 |
| 2 | 소탕 | 없음 | 적 0이고 마지막 웨이브가 아니면 휴식 180틱 → 0 |

**적 AI**: 매 틱 목표 재계산. 강습병은 코어, 나머지는 가장 가까운 생존 플레이어(없으면 코어). 포수는 320px 거리 유지(가까우면 후퇴, ±40px 안이면 정지). 접촉 시 쿨다운마다 피해 + 넉백(대시 중이면 둘 다 없음). 포수는 600px 안에서 1.5초마다 사격. 적끼리 겹치면 밀어내고 경기장 안에 가둔다.

**부활**: 2인만. 쓰러진 짝의 70px 안에 머물면 틱당 +1, 120틱이면 최대 체력 50%로 부활. 떠나면 틱당 -2.

### SIM-06 봇 AI (`sim/bot.ts`)

**입력**: 상태, 봇 번호, 봇 기억(`BotMemory`), 솜씨(`BotSkill`). **출력**: `InputFrame`.

### SIM-09 위치 기록 (`sim/history.ts`)

64틱 링 버퍼(`tick % 64` 칸). 플레이어는 칸마다 두 명의 위치·대시 상태, 적은 칸마다 최대 64기의 id·위치. 조회는 버퍼보다 오래된 틱이면 가장 오래된 기록으로, 미래나 덮어쓴 칸이면 null(호출자가 현재 위치로 판정).

### NET-05 세션 (`net/session.ts`)

**상태**: `connected` → (끊김) `reconnecting` → `connected` 또는 `failed` / 사용자가 닫으면 `closed`.

| 사건 | 처리 |
|------|------|
| 전송로 닫힘 | 방을 만든 쪽이고 시그널링이 살아 있으면 유예 시작(상대 재입장 대기), 아니면 `rejoin()` |
| 시그널링 닫힘 | `rejoin()`: 새 소켓 → 토큰으로 재입장 → 재협상. 700ms 간격 반복, `room_not_found`·`bad_token`이면 포기 |
| `peer_disconnected` | 유예 시작 |
| `peer_rejoined` / `peer_joined` | 재협상 |
| `peer_left` | 실패(`peer_left`) |
| `use_relay` 신호 | 릴레이로 전환 |
| 유예 10초 경과 | 실패: 재접속 시도 중이었으면 `rejoin_failed`, 아니면 `peer_left` |

처리기가 하나도 없는 동안(장면 전환 중) 도착한 **event 채널 메시지는 16개까지 보관**했다가 처음 붙는 처리기에 넘긴다. input 채널 메시지는 버린다.

### SYN-03 호스트 동기화 (`game/sync/HostSync.ts`)

**입력**: 내 입력(매 틱), 참가자 입력 패킷, 참가자 캐릭터 패킷.
**처리**: 참가자 입력을 틱 순 큐에 넣는다(중복 틱·이미 적용한 틱은 버림, 6개 초과 시 오래된 것 버림). 매 틱 큐에서 하나를 꺼내 적용(없으면 마지막 입력 유지). 참가자 탄 되감기 양 = `round(RTT/2 → 틱) + 6`, 상한 대전 12틱·협동 24틱.
**출력**: 3틱마다 스냅샷(input 채널), 경기 끝과 재접속 직후에는 event 채널.

### SCN-04 아레나 (`game/scenes/ArenaScene.ts`)

**프레임 처리(`update`)**
1. 재접속 중이면 시뮬레이션 정지, 안내 표시
2. 참가자가 권위를 아직 못 받았으면 대기 안내, 12초 넘으면 연결 실패로 종료

## 6. 통신 명세

### 6.1 채널

| 채널 | WebRTC 설정 | 싣는 것 |
|------|------------|---------|
| `input` | 순서 없음, 재전송 0회 | 입력(참가자→호스트), 스냅샷(호스트→참가자) |
| `event` | 순서 보장, 재전송 | 캐릭터 선택, 재경기 신호, 마지막·재동기 스냅샷, RTT 핑 |

릴레이일 때는 한 소켓에 `[채널 번호 1바이트][패킷]`으로 실어 보낸다(0 input, 1 event).

### 6.2 게임 패킷 (바이너리)

다중 바이트 값은 빅엔디언. 첫 바이트가 종류.

**입력 `0x01`** (20바이트, 참가자→호스트, 60Hz)

| 위치 | 크기 | 내용 |
|------|------|------|
| 0 | 1 | 0x01 |
| 1 | 4 | 최신 입력 틱 (u32) |
| 5 + 5k | 5 | k번째 프레임 (k=0 최신, 1·2는 직전 틱): 이동 x·y, 조준 x·y (각 i8, 값×127), 버튼 u8 |

버튼 바이트: bit0 fire, bit1 dash, bit2 skill, bit3~4 swapTo.

**캐릭터 `0x02`** (3바이트, 양방향): `[0x02][파티마 번호][기본 무기 번호]`.

**재경기 `0x04`** (1바이트, 양방향): `[0x04]`.

**스냅샷 `0x03`** (가변, 호스트→참가자, 20Hz)

| 부분 | 크기 | 필드 |
|------|------|------|
| 헤더 | 21 | 종류 u8, 틱 u32, 확인 틱 u32, 다음 탄 id u32, 경과 틱 u32, 모드 u8(1 협동), 인원 u8, 탄 수 u8, 픽업 수 u8 |
| 플레이어 ×2 | 33 each | 파티마 u8, x f32, y f32, hp u16, 조준 f32, 발사 쿨 u8, 대시 u8, 대시 쿨 u8, 부활 u8, 무기 u8, 기본 무기 u8, 무기 틱 u16, 부스트 틱 u16, 넉백 x f32, 넉백 y f32 |
| 통계 ×2 | 28 each | 발사, 명중, 가한 피해, 받은 피해, 처치, 대시, 다운 (u32 ×7) |
| 탄환 ×N | 28 each | id u32, 소유자 u8, 종류 u8, spawnTick u32, x·y·vx·vy f32, 피해 u8, 수명 u8 |
| 픽업 ×K | 13 each | id u32, 종류 u8, x·y f32 |
| 협동부 | 11 | 코어 HP u16, 웨이브 u8, 단계 u8, 타이머 u16, 다음 적 id u32, 적 수 u8 |
| 적 ×M | 15 each | id u32, 종류 u8, x·y f32, hp u16 |

목록마다 최대 255개(탄은 최신 255개). 탄의 되감기 양·맞힌 목록, 적의 쿨다운, 스폰 큐, 난수 상태, 난이도는 싣지 않는다.

**RTT 핑** (10바이트, event 채널): `[0xF0|0xF1][순번 u8][보낸 시각 f64]`. 0xF0을 받으면 머리만 0xF1로 바꿔 돌려주고, 0xF1을 받으면 `지금 - 보낸 시각`이 RTT.

### 6.3 시그널링 메시지 (JSON)

**클라이언트 → 서버**

| t | 필드 | 설명 |
|---|------|------|
| `create_room` | | 방 만들기 |
| `join_room` | code | 참가 |
| `rejoin` | code, token | 끊긴 자리 되찾기 |
| `signal` | data | 상대에게 전달 (offer/answer/ice/use_relay) |

**서버 → 클라이언트**

| t | 필드 | 설명 |
|---|------|------|
| `room_created` | code, token | 방 생성됨 |
| `room_joined` | code, token | 참가됨 |
| `rejoined` | code, role | 자리 되찾음 |
| `peer_joined` | | 상대가 새로 들어옴 (협상 시작) |
| `peer_disconnected` | | 상대가 잠깐 끊김 |
| `peer_rejoined` | | 상대가 돌아옴 |
| `peer_left` | | 상대가 떠남 (최종) |
| `signal` | data | 상대의 협상 메시지 |
| `error` | code | `room_not_found` `room_full` `bad_token` `bad_message` |

### 6.4 연결 절차

```
방장                      서버                       참가자
 create_room ──────────►
 ◄────────── room_created(code, token)      (QR·코드 표시)
                                ◄────────── join_room(code)
                          room_joined ──────────►
 ◄────────── peer_joined
 offer ──── signal ────►  ──── signal ──────►
                          ◄──── signal ─────── answer
 ◄──── signal ─────────
 ice ⇄ ice (양방향)
 DataChannel 2개 열림 → P2P 시작
 (5초 안에 안 열리면: use_relay 신호 → 양쪽 모두 릴레이)
```

## 10. 빌드·배포 명세

### 10.1 개발 환경 준비

```bash
git clone https://github.com/k82022603/pocket-arena-shooter.git
cd pocket-arena-shooter
npm install
```

npm 워크스페이스라 루트에서 한 번이면 `apps/web`, `apps/signaling`, `packages/protocol`의 의존성이 모두 설치된다. 초상 일러스트는 저장소에 없으므로, 보려면 `apps/web/public/fatima/`에 직접 넣는다(이름은 그 폴더의 README 참조). 없어도 게임은 동작한다.

| `npm run play -- https` | 위와 같고 자체 서명 https (폰 카메라 QR 스캔용) | 인증서 경고를 한 번 수락 |

### 10.3 빌드 산출물 (`apps/web/dist/`)

| 파일 | 내용 |
|------|------|
| `index.html` | 진입 HTML (회전 안내 포함) |
| `assets/index-<해시>.js` | 앱 전체 번들 (Phaser 포함, 약 1.7MB, gzip 약 430KB) |
| `assets/index-<해시>.css` | 오버레이·회전 안내 스타일 |

해시가 붙은 파일은 내용이 바뀌면 이름도 바뀌어 캐시가 꼬이지 않는다. `dist/`는 `.gitignore`에 있어 커밋되지 않는다.

### 10.4 시그널링 서버 배포 (Render)

`render.yaml` 블루프린트를 쓴다.

1. https://dashboard.render.com → New → Blueprint → 이 저장소 선택 → Apply
2. 설정 내용(블루프린트가 자동 적용): Node 22, 무료 플랜, 싱가포르 리전, 빌드 `npm ci`, 시작 `npm run start -w apps/signaling`, 헬스체크 `/healthz`
3. 배포가 끝나면 `https://<서비스 이름>.onrender.com/healthz`가 `{"ok":true,"rooms":0}`을 주는지 확인
4. 클라이언트에 줄 주소는 `wss://<서비스 이름>.onrender.com`

무료 플랜은 15분 동안 요청이 없으면 잠들고, 첫 접속 때 깨어나는 데 30~60초 걸린다. 방은 메모리에만 있으므로 서버가 재시작되면 진행 중인 방이 사라진다.

### 10.5 웹 앱 배포 (GitHub Pages)

`.github/workflows/pages.yml`, 수동 실행 전용.

1. 저장소 Settings → Pages → Source를 **GitHub Actions**로
2. Settings → Secrets and variables → Actions → **Variables**에 `SIGNALING_URL` = `wss://<서비스 이름>.onrender.com`
3. Actions 탭 → "Deploy web to GitHub Pages" → Run workflow
4. 워크플로가 하는 일: Node 22 → `npm ci` → `npm run build -w apps/web`(`VITE_BASE=/<저장소 이름>/`, `VITE_SIGNALING_URL=<변수>`) → `apps/web/dist` 업로드 → Pages 배포
5. 주소: `https://<계정>.github.io/<저장소 이름>/`

### 10.6 개발 서버만 쓰고 시그널링은 호스팅된 것을 쓸 때

`apps/web/.env`에 한 줄을 적는다(이 파일은 커밋되지 않는다).

```
VITE_SIGNALING_URL=wss://<서비스 이름>.onrender.com
```

### 10.7 배포 후 확인 절차

| 순서 | 확인 | 기대 |
|------|------|------|
| 1 | 시그널링 `/healthz` | `{"ok":true,...}` |
| 2 | 웹 주소를 PC에서 열기 | 타이틀이 뜬다 |
| 3 | 혼자 하기 대전 한 판 | 봇과 경기, 결과 화면 |
| 4 | 폰 두 대로 방 만들기 → QR 참가 | 연결됨 (webrtc), 경기 시작 |
| 5 | `?debug=1`로 열어 진단 줄 | RTT 수십 ms 이하, 호스트 약 60t/s |
| 6 | 한쪽 Wi‑Fi를 잠깐 끊었다 다시 연결 | "재연결 중" 후 이어짐 |
| 7 | 홈 화면에 추가 후 아이콘으로 실행 | 가로로 열림 |

자세한 실기 항목과 합격 기준은 [실기 테스트 가이드](실기_테스트_가이드.md).

### 10.8 빌드·배포 문제 해결

| 증상 | 원인 | 조치 |
|------|------|------|
| 폰에서 주소가 안 열림 | `localhost`로 열었거나 다른 Wi‑Fi | 터미널의 LAN 주소 사용, 같은 Wi‑Fi, Windows 방화벽 허용 |
| QR 스캔 버튼이 흐림 | http로 접속 | `npm run play -- https` |
| 배포본에서 방 만들기가 오래 걸림 | Render 무료 플랜이 잠듦 | 30~60초 기다리기 |
| 배포본에서 "signaling connection failed" | `SIGNALING_URL` 미설정·오타, `ws://` 사용 | Variables 확인, https 페이지에서는 `wss://` |
| 새 버전이 안 보임 | 서비스워커가 옛 버전 제공 | 페이지를 닫았다 다시 열기 (자동 교체), 안 되면 사이트 데이터 삭제 |
| 개발 중 화면이 주기적으로 새로고침됨 | 소스 저장 시 개발 서버의 핫 리로드 | 정상. 배포본에는 없다 |
| 빌드 경고 "chunk size" | Phaser 번들이 큼 | 한도를 1600KB로 올려 두었다. 무시해도 된다 |

| 문서 대조 | `npm run check:docs` | 개발자 매뉴얼 파일 지도·검사 목록·검사 개수 | "문서 수치 전부 일치" |
| 실기 | [실기 테스트 가이드](실기_테스트_가이드.md) | 폰 두 대로 연결·조작·동기화 | 가이드의 합격 기준 |
