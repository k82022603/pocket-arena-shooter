# 실기 테스트 가이드

실제 폰에서 무엇을 어떻게 확인하는지, 합격 기준은 무엇인지 정리한 체크리스트.

- **작성일**: 2026-09-19
- 헤드리스 검사와 브라우저 자동 조작으로는 잡히지 않는 것만 다룹니다. 세 단계의 역할 구분은 [테스트 방식과 헤드리스](테스트_방식과_헤드리스.md) 참조
- 조작과 게임 규칙은 [게임 매뉴얼](게임_매뉴얼.md), 내부 동작은 [개발자 매뉴얼](개발자_매뉴얼.md) 7장

## 1. 준비

노트북에서 한 줄로 서버 두 개를 띄웁니다. Windows는 `play.cmd` 더블클릭도 같습니다.

```bash
npm run play
```

터미널이 접속 주소를 찍어줍니다.

```
  게임 주소: http://172.30.1.81:5173/
  폰을 같은 Wi‑Fi에 연결하고 위 주소를 열거나, 방 만들기 QR을 찍으세요.
```

**주소는 고정이 아닙니다.** Wi‑Fi를 옮기거나 재부팅하면 바뀌므로 매번 터미널 출력을 보세요. `localhost`는 폰 자신을 가리키므로 폰에서는 절대 열리지 않습니다.

체크:

- [ ] 폰과 노트북이 **같은 Wi‑Fi**에 있다
- [ ] Windows 방화벽 허용 요청을 수락했다
- [ ] 폰을 가로로 돌렸다. 세로면 회전 안내가 덮는다
- [ ] 터미널에 LAN 주소를 찾지 못했다는 경고가 없다

카메라로 QR을 스캔하는 기능만 https가 필요합니다. 그때는 이렇게 띄우고 인증서 경고를 한 번 수락합니다.

```bash
npm run play -- https
```

## 2. 진단 화면 읽기

주소 끝에 `?debug=1`을 붙이면 좌상단에 진단 한 줄이 나옵니다. 평소에는 화면을 가리지 않도록 숨겨져 있습니다.

```
RTT 412ms webrtc/guest snap 12 pending 3 fix 41 smooth 5.8px snapped 0 shots 2 rejected 1
```

### 공통 앞부분

| 필드 | 뜻 | 정상 |
|------|-----|------|
| `RTT` | 왕복 지연. 호스트가 핑으로 측정 | 같은 Wi‑Fi면 10~40ms |
| `webrtc` / `relay` | 전송 경로. `relay`면 P2P가 실패해 서버 중계로 내려간 것 | `webrtc` |
| `host` / `guest` / `solo` | 이 기기의 역할 | 의도한 역할 |

### 방을 만든 쪽 (host)

| 필드 | 뜻 | 정상 |
|------|-----|------|
| `queue` | 아직 처리 못한 게스트 입력 수 | 0~2 |
| `drop` | 큐가 넘쳐 버린 입력 누적 수 | 회선이 좋으면 0에 가깝게 유지 |
| `rewind` | 지금 몇 틱을 되감아 판정하는지 | 대전 최대 12틱, 협동 최대 24틱 |

`rewind`가 협동에서 12를 넘어 24까지 올라가는지가 모드별 상한이 실제로 걸리는지 보는 지표입니다.

### 참가한 쪽 (guest)

| 필드 | 뜻 | 정상 |
|------|-----|------|
| `snap` | 보관 중인 스냅샷 수 | 2 이상 |
| `pending` | 아직 호스트가 확인하지 않은 내 입력 수 | RTT에 비례. 회선이 좋으면 0~4 |
| `fix` | 재조정이 일어난 누적 횟수 | 손실이 있으면 증가. 그 자체는 정상 |
| `smooth` | 지금 화면이 실제 위치에서 떨어진 거리 | 대개 0, 보정 중 수 px. 48px을 넘지 않음 |
| `snapped` | 스무딩 없이 즉시 붙인 누적 횟수 | 평상시 **0** |
| `shots` | 화면에 있는 내 예측 탄 수 | 무기에 따라 다름 |
| `rejected` | 호스트가 인정하지 않아 지운 예측 탄 누적 수 | 손실 10%에서 발사 10발당 1발 정도 |

`?debug=1`이면 콘솔 훅도 열립니다. 폰에서는 콘솔을 쓰기 어려우니 노트북 탭에서 씁니다.

```js
window.__link.debugDrop('transport')   // 전송 계층만 강제로 끊어 재접속 시험
window.__link.debugDrop('signaling')   // 시그널링만 강제로 끊기
window.__game                          // Phaser 게임 인스턴스
```

## 3. 폰 한 대로 확인할 것

혼자 하기로 들어가면 됩니다. 1:1 대전은 AI가 상대로 붙습니다.

| 항목 | 합격 기준 |
|------|-----------|
| 이동 | 왼쪽 절반 아무 곳을 드래그하면 그 지점에 스틱이 생긴다 |
| 조준·발사 | 오른쪽 절반 드래그로 조준, 30% 이상 밀면 자동 연사 |
| 대시 | `DASH` 버튼이 엄지에 닿는 위치에 있고, 대시 중 탄을 통과한다 |
| 무기 교체 | `무기 ▸ …` 버튼 탭으로 순환하고, 교체 직후 0.3초 발사가 막힌다 |
| 엄지 가림 | 스틱을 잡은 손이 내 캐릭터나 HP 바를 가리지 않는다 |
| 프레임 | 파티클이 많이 터질 때도 눈에 띄게 끊기지 않는다 |
| 저사양 대응 | 느린 기기에서 처음 3초 뒤 파티클이 줄어든다 |
| 소리 | 첫 터치 후 발사·폭발음이 나고, 타이틀 🔊로 음소거된다 |
| 화면 꺼짐 | 아레나에서 손을 떼고 있어도 화면이 꺼지지 않는다 |
| 회전 안내 | 세로로 돌리면 안내가 덮고, 가로로 돌리면 사라진다 |
| PWA 설치 | 타이틀의 설치 버튼 또는 브라우저 메뉴로 홈 화면에 추가된다 |
| 설치 후 실행 | 홈 화면 아이콘으로 열어도 정상 동작한다 |
| 협동 1인 | 3웨이브부터 강습병이 나온다. **1인은 부활이 없어 한 번 다운되면 끝**이라는 점이 납득되는 난이도인지 본다 |
| 협동 코어 | 상단 중앙의 코어 HP가 줄어드는 것이 보인다. 특히 **포수를 방치했을 때** 내가 안 맞아도 줄어든다 |

## 4. 두 대로 페어링 확인

참가 경로가 세 가지입니다. 각각 한 번씩 밟아보세요.

1. **폰 기본 카메라로 QR 촬영** → 열린 링크로 들어가 타이틀에서 파티마·무기를 고른 뒤 `이 파티마로 참가`
2. **앱 안 `QR 스캔`** → 타이틀 → 참가하기 → `QR 스캔`. https가 아니면 버튼이 비활성
3. **코드 입력** → 6자리 숫자

| 항목 | 합격 기준 |
|------|-----------|
| QR 주소 | QR 아래에 표시된 주소가 `localhost`가 아니라 노트북 LAN IP다 |
| 링크 참가 후 선택 | QR로 들어가도 파티마와 무기를 고른 뒤 입장한다 |
| 새로고침 내구성 | 참가 화면에서 탭을 새로고침해도 초대 코드를 다시 묻지 않는다 |
| 연결 경로 | 진단 줄이 `webrtc`다. `relay`면 Wi‑Fi가 기기 간 통신을 막고 있다 |
| 상대 표시 | 두 캐릭터의 실루엣이 서로 구분된다 |

## 5. 동기화와 협동 모드 확인 (핵심)

여기가 실기에서만 제대로 보이는 부분입니다. 둘 다 **참가한 쪽**에서만 의미가 있습니다. 방을 만든 쪽은 지연이 0이라 해당되지 않습니다.

게스트 주소에 진단과 지연 주입을 함께 붙입니다.

```
http://172.30.1.81:5173/?join=123456&debug=1&lag=200&jitter=40&loss=10
```

### 5.1 보정 스무딩 (1:1 대전)

1. 위 주소로 참가해 1:1 대전을 시작한다
2. 방향을 계속 바꾸며 좌우로 움직인다
3. 내 캐릭터를 본다

| 확인 | 합격 기준 |
|------|-----------|
| 순간이동 | 내 캐릭터가 툭 튀지 않고 미끄러지듯 따라붙는다 |
| `smooth` | 값이 오르내린다. 보정이 실제로 일어나는 중이라는 뜻 |
| `smooth` 상한 | 48px를 넘지 않는다 |
| `snapped` | **0을 유지한다** |
| 명중 감각 | 스무딩과 무관하게 조준한 대로 맞는다 |

`snapped`가 0이 아니면 96px을 넘는 어긋남이 생긴 것입니다. 부활이나 재접속 직후가 아니라면 보고 대상입니다.

### 5.2 적 대상 되감기 (협동 방어전)

1. 호스트가 협동 방어전으로 방을 만든다
2. 게스트가 위 주소로 참가한다
3. 움직이는 **척후병**(빨간 원)을 **앞질러 조준하지 말고 정면으로** 쏜다

| 확인 | 합격 기준 |
|------|-----------|
| 명중 | 화면에서 맞힌 적이 실제로 피해를 입는다 |
| 호스트 `rewind` | 12를 넘어 최대 24까지 올라간다 |
| 대전과 비교 | 같은 실험을 1:1 대전에서 하면 상한이 12라 고지연에서 조금 앞질러야 한다 |

척후병은 초당 150px로 움직이고 판정 반경은 18px입니다. 되감기가 없으면 200ms에서 30px 어긋나 빗나갑니다.

### 5.3 지연 주입이 동작하는 원리

`?lag`은 URL을 붙인 탭에만 적용되고, 그 탭의 송신과 수신을 각각 `lag`만큼 늦춥니다. 호스트는 핑으로 왕복 시간을 재기 때문에 게스트 쪽에만 붙여도 호스트가 측정하는 RTT가 약 `2 × lag`만큼 올라가고, 되감기 양이 따라 커집니다.

| 옵션 | 효과 |
|------|------|
| `?lag=200` | 편도 200ms 지연. 진단 줄의 RTT가 약 400ms로 오른다 |
| `?jitter=40` | 지연을 0~40ms 무작위로 흔든다 |
| `?loss=10` | 패킷 10% 손실. **입력 채널에만** 적용된다 |
| `?debug=1` | 진단 줄과 콘솔 훅 |
| `?join=123456` | 해당 방으로 바로 참가 |

### 5.4 협동 방어전 고유 흐름 (2인)

되감기와 별도로, 협동 모드에만 있는 흐름은 실기에서만 제대로 보입니다.

| 확인 | 합격 기준 |
|------|-----------|
| 웨이브 배너 | 웨이브가 바뀔 때 배너가 뜨고 상단 중앙의 번호가 오른다 |
| 3초 휴식 | 웨이브 사이에 적이 없는 3초가 있다 |
| 등장 방식 | 한꺼번에 쏟아지지 않고 **0.67초 간격으로 한 기씩** 네 변에서 나온다 |
| 소탕 게이트 | 마지막 한 기를 남기고 기다리면 **다음 웨이브가 시작되지 않는다** |
| 포수의 유탄 | 포수를 방치하면 내가 맞지 않아도 **코어 HP가 줄어든다** (한 발에 8) |
| 강습병 | 3웨이브부터 나오고 플레이어를 무시하고 코어로 직행한다 |
| 아군 피해 없음 | 짝을 향해 쏴도 피해가 들어가지 않는다 |
| **부활** | 다운된 짝 곁(70px)에 2초 머물면 절반 HP로 살아난다. 진행 표시가 보인다 |
| 부활 이탈 | 채우다 벗어나면 진행도가 **두 배 속도로** 줄어든다 |
| 코어 통과 | 코어를 엄폐물로 쓸 수 없다. 플레이어와 적이 그냥 통과한다 |
| 대시 무적 | 포수의 사격을 대시로 통과할 수 있다 |
| 승리 화면 | 10웨이브를 전부 소탕하면 승리로 끝나고 도달 웨이브와 코어 HP가 나온다 |
| 패배 화면 | 코어가 0이 되거나 전원 다운이면 패배로 끝난다 |

한 경기가 **최소 2분 20초**입니다. 짧게 확인하려면 1웨이브에서 일부러 코어 앞에 서서 강습병을 통과시켜 패배 화면만 먼저 보는 방법이 있습니다.

참고로 헤드리스 자동 플레이 측정에서 **1인 방어는 5~7웨이브에서 끝났고 클리어하지 못했습니다.** 그때 코어는 평균 400/500이 남아 있었으므로, 1인에서 지는 원인은 코어가 아니라 플레이어 다운입니다. 실기에서 1인 클리어가 안 되더라도 버그가 아닙니다. 2인은 아트로포스 조합이 가장 안정적이고 클로소는 클리어가 어렵습니다.

## 6. 끊김·재접속·재경기

| 절차 | 합격 기준 |
|------|-----------|
| 게스트 폰의 Wi‑Fi를 끄고 5초 안에 다시 켠다 | 양쪽에 `재연결 중… (n)` 이 뜨고 시뮬레이션이 멈춘다 |
| 10초 안에 복구 | 끊긴 지점부터 이어진다. 처음부터 다시 시작하지 않는다 |
| 20초 이상 방치 | 남은 쪽 승리로 결과 화면에 간다. 협동은 패배 |
| 노트북 탭에서 `window.__link.debugDrop('transport')` | 위와 같은 재접속 흐름을 즉시 재현할 수 있다 |
| 결과 화면에서 한쪽만 `다시 하기` | `상대를 기다리는 중…`으로 대기하고, 상대 화면에 요청이 표시된다 |
| 양쪽 모두 `다시 하기` | 함께 새 판이 시작된다 |
| 새 판의 무기 | 타이틀에서 고른 기본 무기로 시작한다 |

클라이언트 재접속 창은 10초, 서버가 슬롯을 붙잡아 두는 시간은 15초입니다.

## 7. 합격 기준 요약

한 바퀴 돌고 아래가 모두 참이면 통과입니다.

- [ ] 진단 줄이 `webrtc`다
- [ ] 같은 Wi‑Fi에서 RTT가 40ms 이하다
- [ ] `snapped`가 0이다
- [ ] `smooth`가 48px를 넘지 않는다
- [ ] 협동에서 호스트 `rewind`가 24까지 오른다
- [ ] 협동에서 마지막 적을 남기면 다음 웨이브가 시작되지 않는다
- [ ] 협동에서 다운된 짝을 곁에서 부활시킬 수 있다
- [ ] 적을 앞질러 조준하지 않아도 맞는다
- [ ] 참가 경로 세 가지가 모두 된다
- [ ] 끊고 10초 안에 다시 붙으면 이어진다
- [ ] 양쪽이 눌러야 재경기가 시작된다
- [ ] 엄지가 캐릭터나 HP 바를 가리지 않는다

## 8. 문제를 보고할 때

아래 네 가지를 함께 남기면 원인을 좁힐 수 있습니다.

1. **진단 줄 전체**를 그대로 (RTT, 경로, 역할, 모든 필드)
2. 접속에 쓴 **URL 전체** (붙인 옵션 포함)
3. 어느 쪽 기기인지 (방 만든 쪽 / 참가한 쪽), 모드 (대전 / 협동)
4. 기기와 브라우저 (예: Android Chrome, iPhone Safari)

## 9. 안 될 때

| 증상 | 확인할 것 |
|------|-----------|
| 폰에서 주소가 열리지 않음 | 같은 Wi‑Fi인지, `localhost`를 쓰지 않았는지, 방화벽 허용 여부 |
| QR 주소에 `localhost`가 들어감 | 개발 서버가 LAN 주소를 못 찾은 경우. 터미널 경고 확인 |
| 앱 안 `QR 스캔`이 비활성 | https로 띄워야 한다. `npm run play -- https` |
| `방을 찾을 수 없습니다` | 호스트가 방 만들기 화면을 유지 중인지, 시그널링 서버 창이 살아 있는지 |
| 진단 줄이 `relay` | Wi‑Fi가 기기 간 통신을 막고 있다. 게스트 모바일 핫스팟으로 바꿔 시도 |
| QR을 찍었는데 코드를 다시 물어봄 | 브라우저를 완전히 새로고침한 뒤 새 QR을 찍는다. 예전 버전이 캐시에 남을 수 있다 |
| 캐릭터 초상이 비어 있음 | 원작 일러스트는 저작권상 저장소에 없다. [넣는 방법](../apps/web/public/fatima/README.md) |
| 소리가 안 남 | 첫 터치 전에는 브라우저가 오디오를 막는다. 화면을 한 번 터치한다 |

규칙만 빠르게 보려면 화면 없이 돌립니다. 지금 26개 항목이 통과하며, 그중 일곱 개가 협동 모드 규칙입니다.

```bash
npm run check:sim
```
