# 연결 방식: 블루투스 대신 Wi‑Fi(WebRTC)를 쓰는 이유

- **작성일**: 2026-09-19

## 블루투스 모드는 없습니다
기획 단계(기획서 5장)에서 확인했듯 **모바일 브라우저는 블루투스로 폰끼리 직접 연결할 수 없습니다.** Web Bluetooth API는 "찾는 쪽(Central)" 역할만 가능하고 "광고하는 쪽(Peripheral)" 역할은 불가능해서 폰 브라우저끼리는 서로를 발견조차 못 합니다. 게다가 iOS(아이폰)는 Web Bluetooth 자체를 지원하지 않습니다.

그래서 "옆 사람과 QR로 바로 붙는다"는 원래 요구는 **같은 Wi‑Fi(또는 핫스팟) 위에서의 WebRTC 직결**로 구현했습니다. 체감 속도와 사용 흐름(QR 찍고 바로 연결)은 블루투스와 동등하거나 더 낫습니다.

## 지금 구조에서 알아둘 점
방 코드를 발급하고 두 폰의 연결을 중개하는 **시그널링 서버**가 지금은 노트북에서 돌고 있습니다. 그래서:

- **같은 Wi‑Fi 안에서**는 문제없이 폰 여러 대로 플레이 가능 (지금 하고 계신 방식)
- **노트북 없이 폰 두 대만으로 밖에서** 하려면 둘 중 하나가 필요합니다:
  - (a) 한 폰의 핫스팟에 노트북도 같이 붙여서 시그널링 서버를 계속 띄워두기
  - (b) 시그널링 서버를 무료 호스팅(Render 등)에 올려서 노트북 없이도 항상 켜져 있게 하기

## (b) 무료 호스팅 배포 (완료)
Render에 시그널링 서버를 무료로 올릴 수 있는 설정을 만들어 두었습니다 — [render.yaml](../render.yaml). 배포하면 노트북을 꺼도 폰들이 인터넷을 통해 방 코드를 주고받을 수 있고, 실제 게임 데이터(위치·발사 등)는 여전히 두 폰 사이 WebRTC로 직접 오가서 지연이 낮게 유지됩니다.

배포 방법과 웹 앱 자체를 GitHub Pages에 올려 URL로 공유하는 방법은 [README.md](../README.md)의 "호스팅" 절을 참고하세요.

## 진짜 블루투스(BLE)가 꼭 필요하다면
인터넷이 전혀 없는 환경(지하, 오지 등)에서 진짜 블루투스로 연결하려면 ESP32 같은 별도 **BLE 브리지 장치**를 두는 방법뿐입니다(기획서의 선택 트랙 M6). 폰 브라우저가 이 브리지 장치에 연결해 서로의 데이터를 중계받는 방식이며, 지금은 구현하지 않았습니다.
